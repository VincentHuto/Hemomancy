# Capability lifecycle and observer sync

## Where state actually lives

[HemoAttachmentTypes](../../src/main/java/com/vincenthuto/hemomancy/common/capability/HemoAttachmentTypes.java) owns serialized attachment types. Most player records are `copyOnDeath`; `SCHOOL_COMBAT` is an attachment on living entities without that policy. [HemoCapabilityRegistrar](../../src/main/java/com/vincenthuto/hemomancy/common/capability/HemoCapabilityRegistrar.java) exposes many player attachments as NeoForge entity capabilities and separately registers item, block-entity, and inventory capabilities. [HemoCapabilityAccess](../../src/main/java/com/vincenthuto/hemomancy/common/capability/HemoCapabilityAccess.java) mixes `getCapability` for public interfaces with direct `getData` for concrete attachments. A missing capability means no provider; a present inactive blood-volume record is still a valid attachment. Do not add a second state container.

`copyOnDeath` handles stored attachment data. It does not send UI snapshots, rebuild tracking-player visuals, clear transient maps, or migrate legacy records. Those operations live in event subscribers across `common/capability/player`, `common/event`, `common/damage`, `common/mission`, `common/antecedent`, `common/manipulation`, and item packages. The [Stage 1 event-order audit](stage-1-capabilities/README.md) records the damage/death phases and the migration-before-snapshot constraints.

The registry contains more player attachments than this event table: some are read only on demand or through other feature services. In particular, [WhiteHumorVolumeEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/unstained/white_humor/WhiteHumorVolumeEvents.java) has no subscribers, so it should not be counted as an existing lifecycle sync path. The [Stage 2 snapshot audit](stage-2-player-snapshots/README.md) compares the exact tendency/vascular packet and fallback behavior before any dispatch extraction.

## Three different recipient contracts

1. **Owner-only UI state:** blood volume, degree, tendencies, vascular map, known arts, knowledge, and most progress packets. A login/dimension/respawn dispatcher can call feature-specific `prepareAndSync` methods, but each method must declare whether it mutates state.
2. **Observer-visible player state:** avatar form, equipment slots/layers, scars, morphling, and muscle memory. These need a current-state packet to the new observer in `StartTracking`, plus update packets to existing trackers when state changes. Sending only to the owner leaves other players stale.
3. **Living-entity state:** [SchoolCombatEvents](../../src/main/java/com/vincenthuto/hemomancy/common/damage/SchoolCombatEvents.java) uses `SCHOOL_COMBAT` on any living target, sends dirty changes to tracking players and self on the entity tick, sends a snapshot to a new tracker, and clears school states on death. It is not a player capability lifecycle.

## Concrete consolidation seam

Create a table or small dispatcher of lifecycle actions keyed by event (`LOGIN`, `DIMENSION`, `RESPAWN`, `START_TRACKING`, `JOIN`, `LOGOUT`) and recipient kind (`OWNER`, `TRACKER`, `TRACKING_AND_SELF`). Keep each feature's preparation, mutation, and payload builder in its current domain class. Start with the owner-only tendency and vascular snapshots, then the observer-visible scar and morphling snapshots. Only merge delivery when the triggers and recipients truly match.

Before changing a hook, record its call order against other subscribers. In particular, bloodline restoration and Clinical Blood recipe reconciliation must precede their owner snapshots, Unstained art grants must precede the known-art snapshot, and respawn cleanup must precede muscle-memory and Body Idiom sync. `PlayerEvent.Clone` should be used only for state that attachment `copyOnDeath` does not already preserve or whose semantics require an explicit copy.
