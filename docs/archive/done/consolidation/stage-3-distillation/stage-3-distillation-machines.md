# Stage 3: Alembic and Retort transaction audit

This is a source audit of the 2026-09-25 checkout. It describes a future consolidation seam; it does not change machine behavior. The [recipe overview](../recipe-pipelines.md) and [screen geometry map](../screens-menus-and-sprites.md) give the surrounding registry and UI context.

## Shared recipe, different machines

Both [GhastlyAlembicBlockEntity](../../../src/main/java/com/vincenthuto/hemomancy/common/tile/harbinger/crafting/GhastlyAlembicBlockEntity.java) and [PallidRetortBlockEntity](../../../src/main/java/com/vincenthuto/hemomancy/common/tile/unstained/crafting/PallidRetortBlockEntity.java) scan `distillation_recipe_type`, take the first matching [DistillationRecipe](../../../src/main/java/com/vincenthuto/hemomancy/common/recipe/DistillationRecipe.java), keep cook progress, increment `recipesUsed` on success, and save it under `RecipesUsed`. They also expose menus with the same first five slot indexes and positions. Their recipe partition is `!isPallid()` for Alembic and `isPallid()` for Retort. The [serializer](../../../src/main/java/com/vincenthuto/hemomancy/common/recipe/serializer/DistillationRecipeSerializer.java) carries optional catalyst, blood input, catalyst-consumption flag, white-humor cost, result count, XP, and cook time in the same recipe format.

### Output components are the main capacity question

Both ordinary `canBurn` methods use `ItemStack.isSameItem`, so outputs with the same item but different data components can stack. Their `burn` methods grow the existing output stack, retaining that stack's components. The Alembic's **advanced brewing** path instead uses `ItemStack.isSameItemSameComponents` in `canAcceptAdvanced`. The shared ordinary predicate should initially retain `isSameItem`; changing to component-aware comparison is a gameplay correction requiring a separate decision and a recipe/result inventory check. The recipe JSON/codec can represent an `ItemStack` result, so the distinction is not merely theoretical.

The capacity predicate also checks `current count + recipe result count` against both the machine maximum and the current stack maximum. When the output is empty, both methods return true after confirming a nonempty recipe result; they do not perform those combined-count checks. Preserve that behavior in a straight extraction, and audit oversize recipe results separately.

## Recipe ledger, XP, and player extraction

Both machines increment a recipe-ID counter with `setRecipeUsed`, load/save `RecipesUsed`, and have near-identical XP rounding and award methods. [GhastlyAlembicBlock](../../../src/main/java/com/vincenthuto/hemomancy/common/block/harbinger/crafting/GhastlyAlembicBlock.java) and [PallidRetortBlock](../../../src/main/java/com/vincenthuto/hemomancy/common/block/unstained/crafting/PallidRetortBlock.java) call `getRecipesToAwardAndPopExperience` on block removal; that path grants XP without a player and clears the ledger.

The separate `awardUsedRecipesAndPopExperience(ServerPlayer)` methods have **no call site in current gameplay Java** (source-wide search). The Retort puts [UnstainedObservances.recordRetortSolution](../../../src/main/java/com/vincenthuto/hemomancy/common/mission/unstained/UnstainedObservances.java) only inside that uncalled method when a hemolytic-solution recipe is awarded to a player. The Retort [menu](../../../src/main/java/com/vincenthuto/hemomancy/common/menu/tile/crafting/PallidRetortMenu.java) uses a plain `FurnaceResultSlot` and does not call this method on extraction. This is a **source-reachability concern**, not a verified in-game failure: trace normal pickup, shift-click, and block removal before changing reward timing or moving the ledger. The block-removal XP path does not call the observance hook.

The Alembic [menu](../../../src/main/java/com/vincenthuto/hemomancy/common/menu/tile/crafting/GhastlyAlembicMenu.java) has an `onTake` override that calls `onPlayerExtract`, and its quick-move path also calls `onPlayerExtract` before `slot.onTake`. The [block entity](../../../src/main/java/com/vincenthuto/hemomancy/common/tile/harbinger/crafting/GhastlyAlembicBlockEntity.java) clears `completedOperation` after a matching extraction, making a second call appear inert, but extraction count and advancement delivery still need a live trace before rewriting the menu. This hook records the completed operation in Advanced Brewing progress; it is different from the unused recipe-award method.

## Inventory and UI boundary

The [menus](../../../src/main/java/com/vincenthuto/hemomancy/common/menu/tile/crafting/GhastlyAlembicMenu.java) and [Retort menu](../../../src/main/java/com/vincenthuto/hemomancy/common/menu/tile/crafting/PallidRetortMenu.java) share input `0` at `(44,32)`, flask `1` at `(155,58)`, result `2` at `(134,32)`, catalyst `3` at `(8,8)`, and flask output `4` at `(134,58)`. Alembic adds dedicated blood input `5` at `(8,32)` and second catalyst `6` at `(8,58)`. Both screens use a 176×176 compact panel, but their fluid widgets and materials differ. [Screens, menus, and sprites](../screens-menus-and-sprites.md) has the complete layout table.

This positional overlap is a UI/layout candidate, not part of the recipe-capacity extraction. The Alembic's dedicated recipe blood slot must not be routed through its reservoir flask-transfer slot. Quick-move routing, sided automation, flask conversions, and result extraction have machine-specific behavior.

## Implementation sequence after this audit

1. Extract only the ordinary distillation result-capacity predicate. Pass the recipe result and current output explicitly; leave recipe lookup, input checks, resource gates, and commit in each block entity. Preserve `isSameItem`, count limits, and the current empty-output rule for this mechanical move.
2. Trace ordinary recipe pickup and shift-click in both machines, plus Alembic advanced output pickup, Retort hemolytic-solution pickup, and block removal. Record item counts/components, recipe ledger contents, XP, and observance/progression events. Resolve the uncalled player-award method and Retort observance path as a separate gameplay change if the trace confirms a gap.
3. Only then consider a recipe lookup helper. Its inputs must include pallid mode and the optional dedicated blood stack; keep first-match selection and do not cache holders across datapack reload without invalidation.
4. Consider a ledger/XP helper after player versus no-player award timing is decided. Preserve `RecipesUsed`, recipe IDs, fractional XP rounding, and Retort-only observance behavior.

No gameplay trace or live GUI review was performed for this documentation stage. A later implementation should verify the directly affected machine interactions and save/reload behavior rather than infer them from successful compilation.
