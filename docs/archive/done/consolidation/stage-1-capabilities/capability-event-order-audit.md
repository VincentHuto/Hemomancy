# Stage 1: capability and entity event order audit

This is a source audit of the 2026-09-25 checkout. It records where a shared event dispatcher would cross a gameplay boundary. It does not establish runtime order among subscribers at the same priority, nor does it prove that a suspected interaction occurs in play. The [storage index](../capability-storage-index.md) and [lifecycle matrix](../capability-lifecycle-and-observer-sync.md) cover persistence and recipients.

The [last-death-memory owner](../../../src/main/java/com/vincenthuto/hemomancy/common/item/harbinger/memory/HematicMemoryToolEvents.java) records position/time in its NORMAL death subscriber. This is another reason to settle the effective-death boundary before merging death callbacks.

## Player lifecycle and observer order

1. **Stored copy:** [HemoAttachmentTypes](../../../src/main/java/com/vincenthuto/hemomancy/common/capability/HemoAttachmentTypes.java) marks 27 player attachments `copyOnDeath`. This preserves serialized records; it does not run feature resets or send packets.
2. **Prepare and migrate:** Blood Volume restores bloodline association at login; Clinical Blood reconciles recipe grants at login; Known Still Arts and Unstained Progress grant eligible arts; Living Staff ensures two forms; Muscle Memory migrates legacy priming at login and clears priming/runtime maps on respawn; Body Idioms clears transient guardrail values on respawn. These are gameplay writes and must precede the corresponding snapshot.
3. **Owner snapshot:** Most knowledge/progress records send to the player on login, respawn, and dimension change. [AntecedentKnowledge](../../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/shared/knowledge/AntecedentKnowledge.java), [ClinicalBloodKnowledge](../../../src/main/java/com/vincenthuto/hemomancy/common/mission/alchemist/ClinicalBloodKnowledge.java), [BodyIdiomEvents](../../../src/main/java/com/vincenthuto/hemomancy/common/manipulation/BodyIdiomEvents.java), and [HematicMemoryToolEvents](../../../src/main/java/com/vincenthuto/hemomancy/common/item/harbinger/memory/HematicMemoryToolEvents.java) are owners outside `common/capability`.
4. **Observer snapshot:** School Combat sends a living target's state on `StartTracking`; avatar, scars, morphling, equipment, and muscle memory send a tracked player's visual state to the new observer. Owner login sync cannot replace these late snapshots.
5. **Logout and clone:** Morphling writes the equipped state back to a jar at logout; Chamber Visit has an explicit clone copy and visit cleanup. Neither operation is a plain owner packet.

### Known manipulation owner snapshot (Stage 1 implementation)

| Boundary | Verified source contract |
| --- | --- |
| Storage and host | `hemomancy:known_manipulations` is a serialized `KnownManipulations` attachment on `EntityType.PLAYER`, exposed by `HemoCapabilityKeys.KNOWN_MANIPULATIONS` through `HemoCapabilityRegistrar`. The attachment has `copyOnDeath`; no clone write is needed for this record. |
| Server mutation owners | `KnownManipulationGrantHelper` learns and equips forms; selection/equip/loadout/vein network handlers update player choices; items, commands, vein mining/travel, and `AvatarManifestationManager` change knowledge, progress, veins, or avatar form. `KnownManipulationEvents.onManipulationUsed` advances mastery. Some callers mutate returned maps/lists or `ManipLevel` directly, so setter-only dirty tracking would miss writes. |
| Preparation | Login calls `grantDegreeOneUtilities` before the owner snapshot. The helper only prepares the grant; the rite caller sends after a successful grant. Packet construction still sanitizes retired manipulations before capture. Entity join clears `lastVeinMineStart`; the next changed-state check sends that cleanup if it follows a lifecycle snapshot. |
| Owner delivery | Login, respawn, and dimension change send `KnownManipulationServerPacket` to the owner. `refreshPlayerDimensions` retains the per-tick dimensions work; the separate `syncChangedOwnerState` tick handler compares serialized authoritative state with the last owner lifecycle/change snapshot and sends only on a difference. Existing direct mutation senders remain for immediate response; a direct sender can be followed by one changed-state tick packet because it does not update this cache. Logout clears the cache. Opening the Synaptic Loadout screen requests a fresh owner snapshot through `KnownManipulationClientPacket`. |
| Observer delivery | The full known-manipulation packet has no observer recipient. `StartTracking` sends `SyncTrackingAvatarPacket` with the tracked player's avatar form to the new observer; avatar changes separately broadcast that visual state. These paths remain in their owners. |
| Client projection | `KnownManipulationServerPacket.handle` writes the owner's client attachment: known map/levels, selected manipulation and memory, veins, avatar form, vein-mining start, equipped names, loadouts, and grandfathered forms. The radial selector, skill tree, Reliquary, loadout screen, diagnostics, and avatar rendering read this local state; observer avatar rendering uses `SyncTrackingAvatarPacket`. |

At 20 ticks per second, the prior tick subscriber sent 20 full owner packets per second per player even while idle, plus lifecycle and direct mutation sends. The new tick path sends zero while the serialized state is unchanged and at most one changed-state packet per tick; lifecycle snapshots and direct sends remain. This is a source-derived cadence, not a network capture. In particular, `UpdateCurrentVeinPacket` and vein-mining start/clear writes lacked direct full-snapshot sends, so the changed-state tick remains necessary. No packet consumer requires an unconditional owner snapshot every tick. `UnstainedProgressEvents` still calls `KnownStillArtEvents.grantEligibleArts` in `syncProgress`, while Known Still Arts also grants on login; that separate preparation boundary remains for a later stage.

## Stage 2 entry criteria

Before extracting a shared lifecycle dispatcher, record for each participating attachment: storage ID and host, server mutation owner, prepare/migrate action, event trigger, recipient, packet, death/cancellation rule, and client projection. The [Stage 2 snapshot audit](../stage-2-player-snapshots/README.md) now maps the first owner-only tendency and vascular pair, including their missing-capability differences and packet handlers. Keep combat mutations, observer snapshots, and special login work in their domain owners. For damage or death consolidation, first trace one direct melee hit, one canceled incoming hit, one absorbed hit, one projectile/school hit, and one canceled player death in a live or focused gameplay run. This document makes no claim those scenarios have been executed.
