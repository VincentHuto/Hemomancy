# Entity and player event phases touching capabilities

This is a representative event-side map for capability-backed mechanics. The event names and phases below come from current gameplay subscribers. Multiple handlers can run for the same hit or death, and the result of one can change what the next sees. See the [Stage 1 event-order audit](stage-1-capabilities/README.md) for priority and cancellation details, [capability lifecycle and observer sync](capability-lifecycle-and-observer-sync.md) for login/respawn/tracking, and [combat and powers](combat-and-powers.md) for school damage provenance.

## Tick, tracking, and other event families

- `PlayerTickEvent.Post` drives [BloodVolumeEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/harbinger/bloodvolume/BloodVolumeEvents.java) income and bloodline pooling, [ArmorSetBonusHandler](../../src/main/java/com/vincenthuto/hemomancy/common/event/ArmorSetBonusHandler.java) equipment effects, [ScarsEntityEventHandler](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/harbinger/scar/ScarsEntityEventHandler.java) scar ticking, [KnownManipulationEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/harbinger/manip/KnownManipulationEvents.java) dimension refresh and sync, [PurityGainEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/unstained/PurityGainEvents.java) Unstained progress, [ToggleableSkillEvents](../../src/main/java/com/vincenthuto/hemomancy/common/event/ToggleableSkillEvents.java) ability state, and more. A shared scheduler should retain each feature's cadence, server gate, and owner. Moving every tick to one giant handler would hide these boundaries.
- `EntityTickEvent.Pre` advances and syncs the living-entity school attachment in [SchoolCombatEvents](../../src/main/java/com/vincenthuto/hemomancy/common/damage/SchoolCombatEvents.java); [SchoolAwareness](../../src/main/java/com/vincenthuto/hemomancy/common/damage/SchoolAwareness.java) reads the same school states to change mob target/navigation. [WhiteHumorPurificationEvents](../../src/main/java/com/vincenthuto/hemomancy/common/event/WhiteHumorPurificationEvents.java) also uses entity Pre/Post ticks for separate purification behavior. Keep entity-wide state distinct from player-only capability exposure.
- `LivingEquipmentChangeEvent` in [ArmorSetBonusHandler](../../src/main/java/com/vincenthuto/hemomancy/common/event/ArmorSetBonusHandler.java) refreshes modifiers; its periodic player tick handles blood-threshold changes that equipment events cannot see. These are complementary invalidation triggers.
- `AdvancementEvent.AdvancementEarnEvent` feeds [SkillPointGainEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/shared/skill/SkillPointGainEvents.java), [PurityGainEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/unstained/PurityGainEvents.java), and [KnownStillArtEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/unstained/stillart/KnownStillArtEvents.java). One advancement can update separate attachments. Share an event-to-domain dispatch map if useful, but keep each reward rule and sync in its owner.
- `PlayerEvent.StartTracking` is a **late observer snapshot** for school combat, scars, avatar, morphling, equipment, and muscle memory. It should not be replaced by player login sync. The target may be any living entity for school state and specifically a player for the other features.

## Most valuable cleanup decisions

1. Write one event-order sheet for a direct player melee hit, projectile hit, periodic school hit, canceled ward hit, player rescue, and mob kill. Record source entity, direct entity, phase, damage before/after, and each attachment mutation. This reveals duplicate reward/drain paths and unwanted reactions.
2. Keep [SchoolHitContext](../../src/main/java/com/vincenthuto/hemomancy/common/damage/SchoolHitContext.java) and `SchoolDamage` as the provenance boundary for school reactions. Other hooks may use the same hit classification, but do not infer a school from a later entity lookup.
3. Standardize small server-side predicates (`is eligible player`, `landed damage`, `direct melee`, `source owner`) only where semantics match. Keep `Pre` modifiers, `Post` payoffs, and cancellable incoming guards separate.
4. For transient maps keyed by UUID/entity ID, list `logout`, `respawn`, `death`, dimension, server stop, and target disappearance cleanup. [MuscleMemoryEvents](../../src/main/java/com/vincenthuto/hemomancy/common/capability/player/harbinger/musclememory/MuscleMemoryEvents.java) already clears several maps on logout/respawn; [HematicSalvageEvents](../../src/main/java/com/vincenthuto/hemomancy/common/event/HematicSalvageEvents.java) has a session cooldown map and clear method. Do not move them into serialized attachments without a gameplay reason.

The first item is now mapped at source level in the [Stage 1 audit](stage-1-capabilities/README.md). Its proposed gameplay traces are still open; the source map does not prove runtime order among same-priority subscribers.
