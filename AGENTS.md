# AGENTS.md — Hemomancy

## Snapshot
- Hemomancy is a Minecraft **NeoForge** mod for `1.21.1` / `21.1.251`, Java `21`, mod id `hemomancy`, package `com.vincenthuto.hemomancy`.
- Start with `src/main/java/com/vincenthuto/hemomancy/Hemomancy.java`, then verify versions and dependency gates in `gradle.properties`, `build.gradle`, and `settings.gradle`.
- Treat current code/resources as authoritative when docs drift; use `docs/HEMOMANCY_REFERENCE.md` for mechanics/status and `docs/LORE_REFERENCE.md` for tone.
- `docs/README.md` maps the documentation: the two references, one topic doc per feature area at `docs/` root (`ENDGAME_PATHS.md`, `SAINT_MAUSOLEUMS.md`, `BRINED_COURT.md`, `CIRCUS.md`, `NPC_DIALOGUE_AND_TRADE.md`, `CARDINAL_RITES.md`, `MANIPULATIONS_AND_CASTING.md`, `BOSSES.md`, ...), `docs/OPEN_QUESTIONS.md`, and `docs/archive/` for finished tracks, old audits and plans (never authoritative). `docs/OPEN_QUESTIONS.md` is the only list of open questions, remaining work and play-and-tune items; a topic doc's "Open questions" section is a pointer to it, never a second list. A change to a system updates its topic doc with the references; an answered question is recorded under "Rulings that bind" in its topic doc and deleted from `docs/OPEN_QUESTIONS.md`, and a built row is deleted there too. The task plans behind its rows are the chunk files in `docs/owner_answers/`.
- The architecture rules, and the index of every guardrail test that enforces them, are in `docs/architecture/ARCHITECTURE_STANDARDS.md`; read it before adding a system. For the longer contributor checklist, see `docs/agents/hemomancy-mod-agent.md`.

## Architecture map
- `Hemomancy.java` is the wiring hub: it registers `common/init/*Init.java` registries, configs, `HemoCapabilityRegistrar`, `PacketHandler`, reload listeners like `ItemInquiryLoader`, and the HutosLib `BookPlaceboReloadListener` serializer.
- Package split is strict: `client/` = renderers/screens/particles, `common/` = gameplay/content/networking/worldgen, `compat/` = optional integrations, `config/` = NeoForge config specs, `mixin/` = `hemomancy.mixins.json` support. Inside them, packages are by function: a feature's block goes in `block/`, its payloads in `network/<feature>`, its player state in `capability/player/...`, and so on, with a named sub-package where several files belong together (`entity/npc/circus`, `world/vein`). Never add a top-level feature folder (`PackageLayoutGuardrailTest`). Client registration lives in `client/registry/` (one class per concern; `KeyMappings`, `EntityRendererRegistrar`, `ModelRegistrar`, ...), world-space effects draw from the one ordered `client/render/world/WorldEffectDispatcher` (no other `RenderLevelStageEvent` subscriber), and HUD drawing is a layer in `client/registry/GuiLayerRegistrar` (no `RenderGuiEvent` handlers; `HudAndWorldDrawingGuardrailTest`). Nothing under `common/` names a `net.minecraft.client` or `hemomancy.client` class, items included (`CommonClientIsolationTest`): item renderers and armour models are registered from `client/item/ItemClientExtensions`, and other client calls go through `common/util/ClientBridge`, which the client installs at setup.
- Player state is attachment/capability-driven. Define/register through `HemoAttachmentTypes`, `HemoCapabilityKeys`, and `HemoCapabilityRegistrar`; read/write through `HemoCapabilityAccess` only. Its `Player` accessors return the attachment itself (no `Optional`); `AttachmentAccessTest` holds the short allow-list of direct readers.
- Owner sync goes through the `PlayerStateSync` table, which `HemoCapabilityRegistrar` sends after every login, respawn and dimension change; do not add per-system lifecycle resends. State changed outside its senders raises the attachment's dirty flag for the end-of-tick flush. A periodic broadcast keeps what it last sent each player in a `LastSent` and sends only a change. Credit owed to an offline player (a proof, a win) is recorded by UUID in `OfflineCredits` and applied at login; that is not a migration. Static per-player or session maps register their clears and logout removal with `TransientServerStateEvents`.
- The mod has not been released, so a change to player data needs no migration: dev worlds may lose old state. `PlayerDataMigrations` and the `PlayerDataVersion` attachment stay as empty infrastructure for after release (the table is empty; versions 1 to 11 are spent, so the next is 12). From then on old player data is rewritten once, at login, by an entry there (next version, a sunset date at least one release out): read the old key once, write the new home, clear the old key. Never run a migration from its own login, respawn or tick handler (`PlayerDataMigrationGuardrailTest`), and never rename keys inside an existing attachment. Durable player state goes in an attachment; a new `getPersistentData()` call needs an entry in `src/test/resources/architecture/persistent-data-allow-list.txt` (`PersistentDataAllowListTest`). A cooldown that survives relog is a `PlayerCooldowns` entry (reset on death and End return) unless it belongs to its system's own attachment; a session cooldown is a UUID-keyed map cleared through `TransientServerStateEvents` (`CooldownTierGuardrailTest`).
- Important state is always present on players, especially `IBloodVolume`; use `volume.isActive()` as the blood-magic opt-in gate instead of capability presence.
- Cardinal Rites share one tick in `HarbingerCardinalRiteEvents`; where kinds differ it asks the rite's `RiteKind` (succession, station upgrade, Working craft, Puppeteer trial, Unstained, countdown, ceremony), and so do `CardinalRiteTermination` and `CardinalRiteCompletion.complete`. Add kind behaviour as a `RiteKind` hook, not an `isRite`/`isWorkingCraft` check there (`RiteKindGuardrailTest`). A kind's saved state is its own object behind `ActiveCardinalRite` and keeps its NBT keys (`ActiveCardinalRiteNbtLayoutTest`). Start rites with `CardinalRiteActivation.tryStart`, whose checks are the ordered `GATES` list; an ordeal wave is a row of `CardinalRiteWave` and a completion effect is the `completion_effect` its recipe names, never a recipe path or wave id compared in code. The `rite_kind_validation` GameTests characterise every kind.
- A chosen dialogue option posts a `DialogueEvent`; `DialogueEventRouter` tries its ordered table of routes and one `<Npc>DialogueEvents` class per NPC (`common/entity/npc/dialogue/route/`). Add an NPC's events to its class or a new class in the table, never another `DialogueEvent` subscriber (`DialogueRoutingGuardrailTest`); `dialogue_route_validation` fingerprints every route.
- NPC trades are data (`data/hemomancy/npc_trade/<speaker>/`), run by `NpcTradeService` from `NpcTradeRequestPacket`; never a `DialogueEvent`, never a memory, kit or progression proof (`NpcTradeGuardrailTest`). Each speaker has one `NpcTradeSides` side, rapport lives in the `NpcTradeLedger` attachment and is per NPC, and `npc_trade_validation` runs every trade kind with a real player.
- `/hemo` is one root in `common/command/HemoCommand` (operators only) wiring one `<Name>Subcommand` class per branch; add a branch as a new class, keeping the syntax pinned by `HemoCommandTreeTest` and the `hemo_command_validation` fingerprints (`HemoCommandStructureGuardrailTest`). The core-loop fixtures are dev-only branches of their own (`temperpool`, `tank`, `vat`, `gouge`, each `.requires(DevCommands::available)`) over `common/command/CoreLoopFixtures`, whose per-player state is a UUID session map cleared through `TransientServerStateEvents`; they are not `/hemo test` scenarios.
- Harbinger and Unstained are mutually exclusive progression paths; changes to degree/purity logic must preserve the reset rules documented in `docs/HEMOMANCY_REFERENCE.md`.
- Networking is NeoForge 1.21 payload-based. Follow `common/network/PacketHandler.java`: each packet uses `CustomPacketPayload`, static `TYPE`, `STREAM_CODEC`, and `playToClient` / `playToServer` registration in its real direction (only `AntecedentEffectPacket` is bidirectional). Adding, removing or re-laying-out a payload means bumping `PacketHandler.PROTOCOL_VERSION` and rewriting `src/test/resources/network/payload-registry.txt`. Send only through the `PacketHandler` facade (`sendToPlayer`, `sendNear`, `sendTracking`, `sendToAll`, `sendToDimension`, `sendToServer`), validate serverbound claims with `ServerboundGuards`, and pace request-and-reply or key-press payloads through `common/util/ServerboundRateLimiter` (session state the hub clears). A client-bound handler that needs client classes is registered as `ClientPayloadHandlers::dispatch`, with its body in `client/network/Clientbound*Handlers`. A payload decodes, validates and calls one service method; the gameplay lives outside `common/network` (`NetworkPackageGuardrailTest`). What another player's client needs to draw a caster's verb (reach, active verb, selected manipulation) is sent by `common/manipulation/verb/VerbPresence` (`PacketSyncVerbPresence`, to trackers, only while a verb is channelled) and read in common code only through `ClientBridge.onlookerReach` / `onlookerSelection` / `onlookerVerb`; never read a remote player's attachments for it. Do **not** add legacy `SimpleChannel` code.
- Datagen lives in `common/data/gen/DataGeneration.java`; `runData` runs two providers: blockstates and item models for what nothing authors. Language, recipes, tags and loot are authored by hand in `src/main/resources`; a generated file with an authored twin is deleted (`GeneratedResourceShadowGuardrailTest`). `DynastyCastlePieceProvider` stays as a dormant regeneration tool.
- Projection and Absorption are verbs, not memories: the active verb is player state (`IKnownManipulations.getActiveVerb`) set by the verb key (`VerbSelection.press`) or by a verb pick on the radial's inner ring (`BloodVerbChoicePacket`, `VerbSelection.choose`, which puts the selected memory down, so the pick is the plain verb); they are never equipped, so the cycle key skips them (CL-2). A selected memory sculpts a verb through `setProjectionSculpting(Sculptings::x)` / `setAbsorptionSculpting(Sculptings::x)` in `ManipulationInit`, and a narrow Sculpting tried ahead of the main one is `addProjectionSculpting` / `addAbsorptionSculpting` (in the order attached; a held channel already open keeps the channel ahead of them all). Only `SculptingDispatcher` runs them, after rites, Saints and Wills and before the plain verb, paying through `BloodManipulation.tryPerformVerbPulse`. A Sculpting that must refuse for reasons of place or right implements `VerbSculpting.admits`, asked on every pulse before Temper or blood is priced; a price or reach that depends on the player is `bloodPerPulse(Player)` / `reachScale(Player)`; one that keeps the channel wherever the aim goes is `holdsChannel()`, its attack-button hit is `takesAccent()` / `accent`, its own walking pace is `movement(Player)`, and one that draws its own link from hand to target returns `drawsOwnStream()` true (`SculptingGuardrailTest`).
- The lash is the one combat strand a memory holds: a `Sculptings` factory calling `Strands.lash(...)` with its feel in `LashProfile` and what sets it apart in `LashStyle` (data on the registration), run only by `StrandService`; `LashTuning` holds the shared feel numbers. The client sends the whip aim and the flick that throws a charged lash (`LashAimPacket`); the server reads no flick from the look and holds the aim to its own limits. While a lash swings the view turns only a capped share of the mouse (`LashCamera` through `MixinMouseHandler`). A click with nothing held is the tap (`LashTapPacket`); a click while a Sculpting holds the channel is that Sculpting's accent (`StrandSnapPacket`). Every strand hit goes through `StrandHits.strike`, targets come from `ManipulationCombatHelper.swept` and `cone`, and the strand package names no manipulation. What a strand skill level is worth lives in the pure `StrandSkills`; Long Strand, Whipcrack and Free Hand also reach the held manipulations through `HeldSkills` (CQ-20 B), and Second Strand is the lash's twin only (CQ-22 A). A skill a client needs to run the caster's motion and the off-hand twin ride `StrandCue`'s own bits (20 to 22; 23 and 24 carry a lash's phase, and an accent cue's fourth bit is 13), never the client's skill cache. The twin is a copy of the open lash, not a second channel. The jet, spray, plant and brand kits stay in `Strands` for tests only while blood on the ground waits (CQ-25); no memory holds one. What Absorption gains from a creature is the `AbsorptionRiders` table keyed by school state (`SculptingGuardrailTest`, `CombatTargetingGuardrailTest`).
- A held manipulation that is not a lash is its own `VerbSculpting` class with its own mechanic (a beam, a dome, a hand of ice, a thrown javelin, a needle volley, a live run, painted fire, a run of blades), never a second user of another's kit and never a recolour of one (the owner's ruling of 2026-11-12, UN-5).
- A block's blood is a `BlockBloodVolume` read only through `ReservoirBlood.settled` (it clots by `CoagulationRules` against the level clock); a multiblock filler resolves to its main block's tank through `ReservoirBlood.tank`; a living holder declares `isLivingVessel()`, a block without a tank `holdsBlood()` false; clot leaves as Formations only through `HeldFormations`; who may draw is `BloodDrawRights`. A sutured machine's state is `BloodRoutingHelper.linkStatus`, kept on the tank as a `ReservoirReadout.Link` (saved only when not `NONE`) and drawn by `BloodVolumeBarWidget`. No machine makes blood, and nothing keeps blood fresh without its keeper.
- Temper, the spendable pool beside Temperament, is the `hemomancy:blood_temper` attachment; a cast or Sculpting pulse charges it only through `TemperCharge` in `BloodManipulation` (planned before pricing, settled after payment), a new source fills it through `TemperCharge` (`fillFromCreature`, `fillFromFood`, `fillFromWill`, `fillFromKept`, `fillFromCarrion`), and catalysts are data in `temper_catalyst/<school>.json`. Temper never refuses: dry costs more blood and lands softer. State that only remembers what was last sent to a client (the Scrying Temper preview in `ManipulationDiagnosticsSync`) is a session map cleared through `TransientServerStateEvents`, never a field on the attachment: reading the attachment creates it on players who had none (`TemperGuardrailTest`).
- Who may be kept (leash, jar, vat) is one rule, `MenagerieRules.canKeep` through `MenagerieLeash.verdict`, which reads the `hemomancy:menagerie_unkeepable` tag, never a class name; a leash lives on the creature and only `MenagerieLeash` runs it; a kept creature is a `KeptSpecimen` in a `SpecimenVessel`. A vessel's screen is the slotless `SpecimenVesselMenu`, its values menu data slots worked out per viewer by `VesselView`, its one button dispatched to the vessel's own `pressBrood`; breeding is run by `SpecimenBrood` with every number in `BroodRules`. What a player knows of a kind's blood is `BloodResearch` (`met`, `recordMet`, examined, studied), never the stack's identified flag, and a draw from an unread kind gives `BloodResearch.temperShare` of its Temper (CL-12) (`StationMenuGuardrailTest`).
- A mark blood leaves on the world (stain, gouge, living vein, Lux trace) is a `GroundMarkBlock` whose rules live in `common/world/ground/GroundNetwork`; gouge functions are data in `gouge_catalyst/<function>.json` (`GougeCatalysts`, mirrored to clients through the `hemomancy:gouge_catalysts` channel in `DatapackSyncChannels`); lit runs are drawn only by `GroundRunRenderer`. A lit run carries its owner (`GroundRunSavedData.Lit`, the six-argument `GroundNetwork.pulse`), and its block edits go through `PlayerBlockEdits` for that owner only while they are online, alive and in the run's level. A furnace burned from outside goes only through `FurnaceHeat.stoke`. Blood Eclipse's field of dark and its carried dome are the session service `DarkFields` (`feed`, `carry`, `drop`), with their numbers in `DarkFieldRules` and `EclipseDomeRules`.
- A crop's growth answers blood through `BloodFedGrowthRules` and one subscriber, `BloodFedGrowthEvents`; fed soil is stamped on the `fed_ground` chunk attachment through `BloodFedGround`. A fungal strain is one row of `common/block/harbinger/plant/FungalStrains` on a `#hemomancy:strain_substrates/*` tag, never a `CropBlock` and never named outside the table, with its assets from `tools/model_export/fungal_strains.py`. Chum pools live in `ChumPools`, poured only by the projection chain's water link; the hunter a pool draws is chosen by `WorldAnswer.drawHunter` and capped across kinds by `#hemomancy:chum_hunters`.
- Blood moved through the Living Staff is recorded only by `LivingStaffGrowth.record`; a digging Living form pays per block only through `LivingDigging`; every ore vein goes through `OreVeins` over `CrawlSession`.
- A block a manipulation takes out of its place for a while is lifted and set through `PlayerBlockEdits.lift` / `settle` and recorded in `LivingLandLedger` until it is back; cling state is the server-owned `hemomancy:cling` attachment with `ClingRules` shared by Venous Cling and the Holdfast morphling. Hematic Cleats are an Armature fitting, the `hemomancy:cleats` component on boots in `hemomancy:takes_cleats`, read through `CleatsFitting` and toggled by `ToggleCleatsPacket`; an Armature upgrade carries it with `CleatsFitting.carry`.
- Blood left in the world is counted only through `common/world/answer/WorldAnswer` into `BloodSpilledLedger` (waste, never work); meals are rows in `data/<ns>/blood_food/` paid by the one meal hook, `DailyLoopEvents.eat`; ambient world-answer spawns pass `WorldAnswer.scavengersAwake`.

## Workflows that matter
- Windows/PowerShell commands from project root: `./gradlew.bat build`, `./gradlew.bat test`, `./gradlew.bat runClient`, `./gradlew.bat runServer`, `./gradlew.bat runData`, `./gradlew.bat runGameTestServer`.
- Run `./gradlew.bat alphaCheck` for JVM contracts, dedicated GameTests, runtime resource errors and packaged asset-path/PNG-header/font-license checks; see `docs/TESTING.md` for the in-game `/hemo test` fixture workflow. Every test-grid GameTest server (`runGameTestServer`, each suite launcher, and `runPlaythroughGameTestServer` for the opt-in playthrough suite) runs under the isolation harness (`src/gameTest/resources/gametest-isolation.mixins.json`, `gametest/GameTestIsolation`: a 64-block grid, two forced margin chunks, a chunk-aligned random origin within a million blocks of 0; `-PgameTestOrigin=x,z`, `-PgameTestMarginChunks=N`). A GameTest that fails once and passes on a re-run is a defect: find the cause and fix it, never re-run it away (`docs/TESTING.md` "Deterministic GameTests"). NeoForge enables a test by its template's namespace, so a suite's tests use templates in the suite's own namespace (`verifyGameTestSuites`). The core-loop fixtures are `/hemo temperpool|tank|vat|gouge`, not `/hemo test`.
- Tests read repository files through the shared helpers in `src/test/java/com/vincenthuto/hemomancy/support/` (`RepoPaths`, `SourceAssertions`, `ResourceReader`); do not add private `read`/`assertContains` copies. New source-text assertions are for architecture guardrails under `.../architecture/` only. `docs/architecture/evidence/source-text-impact-map.csv` lists which tests read which files; regenerate it with `python gradle/source-text-impact-map.py`.
- `tools/model_export/` (the model generators that tests read), `tools/review/` (multi-client review launchers), `tools/circus/*.py` (the troupe's body and faculty builders), the mausoleum generator (`tools/worldgen/mausoleum_complexes.py` + `tools/worldgen/mausoleum/`) and the Brined Court generators (`tools/worldgen/brined_court_seats.py`, `tools/worldgen/brined_court_outposts.py` + `tools/worldgen/brined_court/`) the Mason's Respite generator (`tools/worldgen/masons_respite.py`), the Harbinger sites generator (`tools/worldgen/harbinger_sites.py` + `tools/worldgen/harbinger_sites/`, the Blood Temple and the Harbinger Outpost's pieces) the wayside sites generator (`tools/worldgen/wayside_sites.py` + `tools/worldgen/wayside/`, the Bog-Body Ossuary Niche and the Sanguine Surveyor Bivouac) and the Circus sites generator (`tools/worldgen/circus_sites.py` + `tools/worldgen/circus/`, the Crimson Troupe site kit and its sampler, the pavilion, the five camps, the abandoned stage and the pavilion's ruin and tenancy overlays; set pieces in `tools/model_export/circus_set_pieces.py`) are version-controlled; the rest of `tools/` stays local. A single review client is a row in the `gradle/review-clients.gradle` table, not a hand-written run block; a row marked `bare: true` also gets a `write<Run>Classpath` task so a `tools/review/` launcher (such as `review-onlooker.ps1`) can start it as plain java after one Gradle call.
- CI dependency preflight is `pwsh -NoProfile -File gradle/verify-dependency-bundle.ps1`. See `docs/DEPENDENCY_PROVISIONING.md` for the pinned JARs/HutosLib source snapshot and clean packaged acceptance.
- `settings.gradle` pulls `../HutosLib` as a composite build when present; otherwise Hemomancy resolves `com.vincenthuto.hutoslib:hutoslib` normally.
- `build.gradle` relies on local jars in `libs/` for TerraBlender, JEI, Create, Building Gadgets 2, WorldEdit, and other dev/runtime integrations; do not assume Maven coordinates exist for every dependency.
- `src/generated/resources` is included as a resource source, but `processResources` excludes duplicates so `src/main/resources` stays authoritative.
- A GameTest stays deterministic: it builds inside its own template (or the all-air `hemomancy:open_room`), gives server-wide state its own batch, never reads light the tick it placed blocks, seeds its rolls (`RandomSource.create(seed)`, `player.getRandom().setSeed`), counts only its own entities, waits on conditions (`thenWaitUntil`) rather than fixed delays, and never reads in one `onEachTick` task what another sets the same tick (they run in hash order; read inside the sequence). Helper coordinates count from one block below the template.
- A review client (`*ClientReview` under `src/gameTest`, a row in `gradle/review-clients.gradle`, user name 16 characters or fewer) takes stills, not a play session: once a new `"kind":"startup"` line appears in `<dir>/operator/journal.jsonl`, drop one `{"op":"create","name":"<user>","seed":"1"}` (or `{"op":"open","name":"<user>"}` on a reused dir) into `<dir>/operator/inbox/`; it places its scene, writes `<dir>/screenshots`, logs `<NAME>_REVIEW captured N` and stops the client. Only one Gradle process at a time, review clients included. `docs/CORE_LOOP_PLAYTEST.md` lists the core-loop ones.

## Project-specific patterns
- Circus pavilion observation and passive acclimation require living, non-spectator players. Preserve earlier discovery and allow ordinary D0/inactive-blood visits; the D4 referral is optional Side work, not a discovery or Main gate.
- Use NeoForge imports (`net.neoforged.*`), `DeferredHolder`, and `Hemomancy.rloc("snake_case_id")` (`ResourceLocationStyleGuardrailTest`); do not introduce `net.minecraftforge.*` or Forge-era provider/registration patterns.
- Player-facing text is an `en_us.json` key, never `Component.literal("English")` (`HardCodedEnglishGuardrailTest`). A message with values is one key with `%s` placeholders: `Component.translatable(key, args)`, or `HemoText.translatable` when an argument is not a component, number, boolean or string (anything else throws in the `TranslatableContents` constructor). A helper that shows text takes a `Component`, not a `String`; names and descriptions in data tables, enum display names and rule reasons are keys too, and datapack JSON text shows through `Component.translatableWithFallback`. English no player reads is counted per file in `src/test/resources/architecture/english-literal-allow-list.txt` (`EnglishLiteralAllowListTest`). Tests read English through `support/EnglishText` and `SourceAssertions.assertShowsEnglish` / `assertNotShowsEnglish`.
- NPC dialogue follows the speaker's sheet in `docs/NPC_VOICES.md` (rhythm, contractions, questions, vocabulary, pronouns); write one speaker at a time and keep each speaker inside the contrast-map targets.
- Shared small helpers live in `common/util`; use them instead of private copies: `HemoEasing` for easing and lerp (never `Mth.smoothstep`, which is quintic), `AttributeModifiers.sync` for held modifiers, `ArmorSets.isFullSet`, `ProgressionGates` for degree and Unstained-stage checks (never compare a degree with a literal), `PatternOrigins` for multiblock placement, `HemoTickers.create` in `getTicker`, and `BlockEntitySync.markAndSync` to save and resend a block entity. `EasingCopyGuardrailTest` and `SmallUtilityGuardrailTest` reject new copies.
- A player pays blood only through `BloodAccounting.pay` (one-off) or `payUpkeep` (recurring), with a named `Source{id, category, reserveProtected}` constant; it records to `BloodFlowLedger` and ends in `BloodVolumeEvents.syncVolume`, the one owner sync (it raises the volume's dirty flag; `PlayerStateSync` flushes it once at the end of the tick, diagnostics at most once a second). Never call `drain(`/`subtractBloodVolume(` on a player volume or send `BloodVolumeServerPacket` directly; `BloodAccountingGuardrailTest` lists the non-player exceptions. Projected blood reaches a block entity through `ProjectedBloodSink` (default on `IBloodReservoir`).
- A caster chooses targets through `ManipulationCombatHelper`: `canHarm(player, target)` is the strict rule, `canHarm(caster, target, Reach.X)` asks a named wider preset (the two Monster filters reach any monster but the caster's allies, G-2b; area damage from armour, Still Arts, Sheolic and Saprovitta asks the strict rule and names the player in its damage source, F-16), and `canHarmFor(source, target)` serves constructs, summons, projectiles and effect holders. A `Monster.class` gather passes `canHarm` in its own arguments (`CombatTargetingGuardrailTest`). Drudge work lives in `DrudgeActions`; heal reductions are `HealModifier` entries applied in one stage; a hit's final amount is changed or read only from its stage in `common/damage/DamageStages` (attackers, defenders, death-saves, readers), and a save from a lethal hit is a Last Rite in its death-save stage (`DamageStageGuardrailTest`); flight is granted and revoked only through `FlightArbiter`, and a revoke keeps flight while another source still grants it (`HealAndFlightGuardrailTest`). "Is it a boss" is `HemoEntityPredicates.isBoss`, which reads only the entity type tag `hemomancy:bosses`; a new boss joins the tag, never a class-name or package check (`BossDefinitionGuardrailTest`). A block a player causes to be placed, broken or converted (a cast, a payload, an item, a block's use, a rite, a projectile, or a run or other world system acting for a player) goes through `common/util/PlayerBlockEdits` (`place`, `mayBreak`, `breakBlock`, `replace`, `lift` / `settle`: game mode, spawn protection, the NeoForge break or place event). `PlayerBlockEditGuardrailTest` scans `common/manipulation`, `network`, `event`, `item`, `block`, `tile`, `rite`, `entity` and `world` and counts every raw `setBlock`, `setBlockAndUpdate`, `destroyBlock` and `removeBlock` per file against `src/test/resources/architecture/player-block-edit-allow-list.txt` (count, file, reason); a guarded call elsewhere in a file does not excuse its raw edits.
- Subscribers are `@EventBusSubscriber(modid = Hemomancy.MOD_ID)` or `@EventBusSubscriber(modid = Hemomancy.MOD_ID, value = Dist.CLIENT)`, never with `bus=`; the `Hemomancy` constructor adds only mod-lifecycle listeners (`RegistrationStyleGuardrailTest`). Client registration uses the event APIs (`registerBlockEntityRenderer`, `registerSpriteSet`, `RegisterClientExtensionsEvent`), never `BlockEntityRenderers.register` or `initializeClient`.
- Registries live in `common/init/*Init.java`; look a custom-registry entry up by name with `RegistryLookup.byName`, register data components with `registerComponentType`, and put creative-tab entries in `CreativeTabInit` (its one WIP list fills the WIP tab and keeps those entries out of the main tab). The main tab runs in banded sections: file a new non-Harbinger entry under its section in `CreativeTabSection` and a Harbinger one in its `CreativeTabGroup` list (unfiled blood memories join the Hematic memories by rank; anything else unfiled falls to the bottom Miscellany section); the client draws the frame and banners in `client/screen/inventory/CreativeTabChrome`. Example: `ManipulationInit` holds the blood-manipulation registry and registers entries like `blood_shot` and `vital_effusion` with cost/rank/temper metadata.
- A wood family is one `WoodSet.register` in `BlockInit`, with its assets, recipes, loot, tags and names generated by `tools/model_export/wood_sets.py`; a planted tree that bites is `HeartwoodTreeRules` + `HeartwoodCoreRules` (`WoodSetResourceTest`, `bloodwood_validation`).
- A Morphling strain is one row of `common/item/harbinger/morphlings/MorphlingStrains` (tempers, passive, house, Cradle flag, Last Rite, polyp family, HUD art, order) with a `HouseMorphlingItem` subclass; code reads the row and never names a `morphling_<strain>` id outside the table and `ItemInit` (`MorphlingStrainTableGuardrailTest`).
- Manipulation implementations live under `common/manipulation/<temper>/`; many also define Drudge AI helpers with `setDrudgeAction(...)`, and what an entity (a Will, Vesper) does when it casts one is attached the same way with `setEntityCast(EntityCasts::x)`; `EntityManipulationEffects.cast` only applies the shared rules (`EntityCastGuardrailTest`). New manipulations usually need the class, a `ManipulationInit` entry, lang/model assets, and related docs.
- Particle data is built through `common/particle/HemoParticleData`. A particle that carries only a colour uses `ColorParticleOptions` (its registered type tells it apart), and every Hemomancy particle type is a `HemoParticleType` with its data's codecs; `ParticleDataGuardrailTest` lists the other data classes and rejects per-factory `createData` helpers.
- Render types are built once: a static constant, a school material from `SchoolRenderTypes` (one `Clock` per family, set by its `begin`), or a `SeededRenderTypes` holder keyed by seed (plus any texture or depth flag) whose factory reads a uniforms record. Never build a `RenderType` per call or per frame; `RenderTypeCachingGuardrailTest` rejects it. A holder keeps two types per seed so queued geometry keeps its uniforms; a caller that asks for one seed with three different uniform sets before drawing must end its batch in between.
- School and rite material vertices (U = shape tile, V = seed tile, alpha × 255) are written through `client/render/world/MaterialQuads`; wrap a seed with `MaterialQuads.seedTile`, never `floorMod(seed, 127)` (`MaterialQuadGuardrailTest`). Ferric and the Outpouring surface marks write through it too; no class keeps its own tile constant.
- Shader noise that two shaders share word for word lives in `assets/hemomancy/shaders/include/noise/*.glsl` and is pulled in with `#moj_import <hemomancy:noise/<name>.glsl>`, one import per include, in dependency order. Seeded noise that reads its shader's own uniforms stays local (`ShaderNoiseIncludeGuardrailTest`). A shader change needs a client launch to prove it compiles; offline validators miss driver errors.
- A boss replays a synced tick counter through `common/entity/boss/BossReplayClock` (`sample` per frame, or `sync` per client tick and `at` per frame) and times moves with `BossMoveTimeline`; never keep a private `tickCount - start` clock or add the partial tick to a synced counter (`BossAnimationClockGuardrailTest`).
- Third-person player poses apply through `client/player/PlayerAnimationRegistry.THIRD_PERSON`, in its listed priority order (staff planting, offset reset, casting, then the first claiming pose of microscope, vial injection, syringe draw, torch breath, Unstained swing, living-weapon stroke, strand stroke, Venous Cling, then the warp chair); `MixinHumanoidModel` calls only the registry. First-person hand renderers keep their pinned `RenderHandEvent` priorities (`PlayerAnimationGuardrailTest`).
- Client animation time comes from `client/render/AnimationTime`: `partialTick()` (reads 1 under `/tick freeze`), `partialTickWhileFrozen()`, `gameTime(level[, partialTick])` and `age(entity, partialTick)`. Render events and HUD layers pass their own partial tick. Every world, item and armour animation freezes under `/tick freeze`, inventory slots included (A-4): items and armour read `AnimationTime.itemMillis()`, which falls back to the wall clock only when no level is loaded. Only screen chrome, the dimension veil, pose cache stamps and the rite bar's ease read the wall clock, each listed with its reason in `AnimationTimeGuardrailTest`; add no new wall-clock animation.
- Screen chrome is shared: borders, bevels, ring borders, corner accents and slot wells come from `ScreenDrawUtils`, and the animated vein background from `VeinBackgroundRenderer` with a per-screen `Style` (`Field`, `Palette`, `Speckles`) that keeps the screen's look. `ScreenChromeGuardrailTest` rejects private copies; a vein field that is different art is listed there with its reason. `ScreenChromeReview` (gameTest, `hemomancy.screenChromeReview`) captures each screen's first frame for before/after comparison.
- For Hemomancy special effects, inspect and prefer the authored Hemomancy/HutosLib visual toolkit before using vanilla particles. Reuse the dynamic glow, cell, tendril, lightning, claw, slash, and related custom effects whenever they can express the intended action; match their color, motion, layering, and intensity to the surrounding blocks, mobs, and items. Vanilla particles are a deliberate fallback for effects the custom suite cannot reasonably express, not the convenience default; `VanillaParticleRatchetTest` pins each file's count in `src/test/resources/architecture/vanilla-particle-allow-list.txt`, so a vanilla particle can leave a file but never arrive. This applies especially to bosses, rites, manipulations, impacts, transitions, and other focal moments; do not let otherwise custom visuals become dominated by generic vanilla particle clouds. Before building or upgrading a focal visual, read [the manipulation visual standard](docs/MANIPULATION_VISUALS.md); Hematic Riposte's layered geometry is the reference bar.
- Sound follows `docs/SOUND.md`: a manipulation's cast sound is its `manipulation.<id>.cast` event (`SoundInit.MANIPULATION_CAST`), played through `ManipulationCastSounds` by player and entity casts; a new sound file is Freesound CC0 or edited (never raw) Sonniss GDC, mono when positional, with a row in `docs/SOUND_CREDITS.md` (`SoundCreditsTest`); Harbinger content takes no bell, brass or copper timbre (copper is Unstained).
- Current resource paths are singular 1.21-style paths already used by this repo: `data/hemomancy/recipe/`, `data/hemomancy/loot_table/`, and `data/hemomancy/dialogue_inquiry/<npc>/<namespace>/<item>.json`. Do not “fix” them to older plural conventions.
- HutosLib owns the book pipeline (`BookPlaceboReloadListener`, the book templates and the guide screens), so check its serializers and reload listeners before inventing local replacements. NPC dialogue is Hemomancy's own (`common/entity/npc/dialogue/`).
- A player-facing system's Liber page is a literal `entry("...")` constant registered in `LiberEntryDefinitions` with a Degree floor (`LiberKnowledgeHelper.unlockForDegree`, or a purity or clarity stage in `unlockForUnstained`) and earlier openers in `LiberDiscoveryEvents`; an unregistered page is hidden from everyone by `MemoBookFilter`, and a new memory must be named on its school's Manipulations page, which carries no mL price and teaches only the held forms that are built (`LiberPageRegistrationGuardrailTest`). A core-loop first is an `impossible`-trigger advancement in the "Core loop firsts" block of `HarbingerAdvancementGranter`, granted by one `grantIfNotDone` where the act happens, after payment; a new one bumps the count of 27 (`CoreLoopTeachingGuardrailTest`).
- A core-loop lesson an NPC teaches is one row of `common/entity/npc/dialogue/CoreLoopLessons`, shown as unread lore cards by `CoreLoopLessonDialogue.append` and taken on the first line of the speaker's own `<Npc>DialogueEvents` by `route/CoreLoopLessonRoutes.teach` (never a new subscriber or route). A lesson opens its Liber pages and nothing else; its ids use `craft` and never a Quest Work word; every key needs a brief, and a number said aloud must change with the code (`CoreLoopLessonsTest`, `CoreLoopLessonGameTests`).
- The blood HUD is one layer, `BloodVolumeOverlay` (`hemomancy:bloodvolume`), laid out by `BloodHudLayout`, shown while a Vascularium Charm or a Titration Bandolier is worn. Its binding is built at runtime from the parts' alpha by `HudAssembly` (`HudBinding`, tiles in `textures/gui/blood_hud/binding_*.png`) and beats on `HudHeartbeat`; frames, fills and vials are drawn 1:1 and never flipped.

## Integration and lore guardrails
- Mana and Artifice, Curios and GeckoLib compat was deleted on 2026-11-03 and those dependencies are gone. A future integration is written fresh against the current API.
- JEI compat is live via the local jar; HutosLib is required infrastructure, not optional sugar.
