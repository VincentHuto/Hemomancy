# AGENTS.md — Hemomancy

## Snapshot
- Hemomancy is a Minecraft **NeoForge** mod for `1.21.1` / `21.1.251`, Java `21`, mod id `hemomancy`, package `com.vincenthuto.hemomancy`.
- Start with `src/main/java/com/vincenthuto/hemomancy/Hemomancy.java`, then verify versions and dependency gates in `gradle.properties`, `build.gradle`, and `settings.gradle`.
- Treat current code/resources as authoritative when docs drift; use `docs/HEMOMANCY_REFERENCE.md` for mechanics/status and `docs/LORE_REFERENCE.md` for tone.
- The architecture rules, and the index of every guardrail test that enforces them, are in `docs/architecture/ARCHITECTURE_STANDARDS.md`; read it before adding a system. For the longer contributor checklist, see `docs/agents/hemomancy-mod-agent.md`.

## Architecture map
- `Hemomancy.java` is the wiring hub: it registers `common/init/*Init.java` registries, configs, `HemoCapabilityRegistrar`, `PacketHandler`, reload listeners like `ItemInquiryLoader`, and the HutosLib `BookPlaceboReloadListener` serializer.
- Package split is strict: `client/` = renderers/screens/particles, `common/` = gameplay/content/networking/worldgen, `compat/` = optional integrations, `config/` = NeoForge config specs, `mixin/` = `hemomancy.mixins.json` support (the dormant `hemomancy.mna.mixins.json` is not loaded while MnA compat is excluded). Client registration lives in `client/registry/` (one class per concern; `KeyMappings`, `EntityRendererRegistrar`, `ModelRegistrar`, ...), world-space effects draw from the one ordered `client/render/world/WorldEffectDispatcher` (no other `RenderLevelStageEvent` subscriber), and HUD drawing is a layer in `client/registry/GuiLayerRegistrar` (no `RenderGuiEvent` handlers; `HudAndWorldDrawingGuardrailTest`). Nothing under `common/` names a `net.minecraft.client` or `hemomancy.client` class except inside an item's `hemomancy$getClientItemExtensions()` (`CommonClientIsolationTest`): other client calls go through `common/util/ClientBridge`, which the client installs at setup.
- Player state is attachment/capability-driven. Define/register through `HemoAttachmentTypes`, `HemoCapabilityKeys`, and `HemoCapabilityRegistrar`; read/write through `HemoCapabilityAccess` only. Its `Player` accessors return the attachment itself (no `Optional`); `AttachmentAccessTest` holds the short allow-list of direct readers.
- Owner sync goes through the `PlayerStateSync` table, which `HemoCapabilityRegistrar` sends after every login, respawn and dimension change; do not add per-system lifecycle resends. State changed outside its senders raises the attachment's dirty flag for the end-of-tick flush. Static per-player or session maps register their clears and logout removal with `TransientServerStateEvents`.
- Old player data is rewritten once, at login, by an entry in `PlayerDataMigrations` (next version, a sunset date at least one release out) gated by the `PlayerDataVersion` attachment: read the old key once, write the new home, clear the old key. Never run a migration from its own login, respawn or tick handler (`PlayerDataMigrationGuardrailTest`), never rename keys inside an existing attachment, and add a `player_migration_validation` fixture (an old-format snapshot plus a run-twice check) with it. Durable player state goes in an attachment; a new `getPersistentData()` call needs an entry in `src/test/resources/architecture/persistent-data-allow-list.txt` (`PersistentDataAllowListTest`). A cooldown that survives relog is a `PlayerCooldowns` entry (reset on death and End return) unless it belongs to its system's own attachment; a session cooldown is a UUID-keyed map cleared through `TransientServerStateEvents` (`CooldownTierGuardrailTest`).
- Important state is always present on players, especially `IBloodVolume`; use `volume.isActive()` as the blood-magic opt-in gate instead of capability presence.
- Cardinal Rites share one tick in `HarbingerCardinalRiteEvents`; where kinds differ it asks the rite's `RiteKind` (succession, station upgrade, Working craft, Puppeteer trial, countdown, ceremony), and so do `CardinalRiteTermination` and `CardinalRiteCompletion.complete`. Add kind behaviour as a `RiteKind` hook, not an `isRite`/`isWorkingCraft` check there (`RiteKindGuardrailTest`). A kind's saved state is its own object behind `ActiveCardinalRite` and keeps its NBT keys (`ActiveCardinalRiteNbtLayoutTest`). Start rites with `CardinalRiteActivation.tryStart`; the `rite_kind_validation` GameTests characterise every kind.
- A chosen dialogue option posts a `DialogueEvent`; `DialogueEventRouter` tries its ordered table of routes and one `<Npc>DialogueEvents` class per NPC (`common/entity/npc/dialogue/route/`). Add an NPC's events to its class or a new class in the table, never another `DialogueEvent` subscriber (`DialogueRoutingGuardrailTest`); `dialogue_route_validation` fingerprints every route.
- `/hemo` is one root in `common/command/HemoCommand` (operators only) wiring one `<Name>Subcommand` class per branch; add a branch as a new class, keeping the syntax pinned by `HemoCommandTreeTest` and the `hemo_command_validation` fingerprints (`HemoCommandStructureGuardrailTest`).
- Harbinger and Unstained are mutually exclusive progression paths; changes to degree/purity logic must preserve the reset rules documented in `docs/HEMOMANCY_REFERENCE.md`.
- Networking is NeoForge 1.21 payload-based. Follow `common/network/PacketHandler.java`: each packet uses `CustomPacketPayload`, static `TYPE`, `STREAM_CODEC`, and `playToClient` / `playToServer` registration in its real direction (only `AntecedentEffectPacket` is bidirectional). Adding, removing or re-laying-out a payload means bumping `PacketHandler.PROTOCOL_VERSION` and rewriting `src/test/resources/network/payload-registry.txt`. Send only through the `PacketHandler` facade (`sendToPlayer`, `sendNear`, `sendTracking`, `sendToAll`, `sendToDimension`, `sendToServer`), and validate serverbound claims with `ServerboundGuards`. A client-bound handler that needs client classes is registered as `ClientPayloadHandlers::dispatch`, with its body in `client/network/Clientbound*Handlers`. A payload decodes, validates and calls one service method; the gameplay lives outside `common/network` (`NetworkPackageGuardrailTest`). Do **not** add legacy `SimpleChannel` code.
- Datagen lives in `common/data/gen/DataGeneration.java`; `runData` runs three providers: blockstates and item models for what nothing authors, and the Circus pavilion template. Language, recipes, tags and loot are authored by hand in `src/main/resources`; a generated file with an authored twin is deleted (`GeneratedResourceShadowGuardrailTest`). `DynastyCastlePieceProvider` stays as a dormant regeneration tool.

## Workflows that matter
- Windows/PowerShell commands from project root: `./gradlew.bat build`, `./gradlew.bat test`, `./gradlew.bat runClient`, `./gradlew.bat runServer`, `./gradlew.bat runData`, `./gradlew.bat runGameTestServer`.
- Run `./gradlew.bat alphaCheck` for JVM contracts, dedicated GameTests, runtime resource errors and packaged asset-path/PNG-header/font-license checks; see `docs/TESTING.md` for the in-game `/hemo test` fixture workflow.
- Tests read repository files through the shared helpers in `src/test/java/com/vincenthuto/hemomancy/support/` (`RepoPaths`, `SourceAssertions`, `ResourceReader`); do not add private `read`/`assertContains` copies. New source-text assertions are for architecture guardrails under `.../architecture/` only. `docs/architecture/evidence/source-text-impact-map.csv` lists which tests read which files; regenerate it with `python gradle/source-text-impact-map.py`.
- `tools/model_export/` (the model generators that tests read) and `tools/review/` (multi-client review launchers) are version-controlled; the rest of `tools/` stays local. A single review client is a row in the `gradle/review-clients.gradle` table, not a hand-written run block.
- CI dependency preflight is `pwsh -NoProfile -File gradle/verify-dependency-bundle.ps1`. See `docs/DEPENDENCY_PROVISIONING.md` for the pinned JARs/HutosLib source snapshot and clean packaged acceptance.
- `settings.gradle` pulls `../HutosLib` as a composite build when present; otherwise Hemomancy resolves `com.vincenthuto.hutoslib:hutoslib` normally.
- `build.gradle` relies on local jars in `libs/` for TerraBlender, JEI, Create, Building Gadgets 2, WorldEdit, and other dev/runtime integrations; do not assume Maven coordinates exist for every dependency.
- `src/generated/resources` is included as a resource source, but `processResources` excludes duplicates so `src/main/resources` stays authoritative.

## Project-specific patterns
- Circus pavilion observation and passive acclimation require living, non-spectator players. Preserve earlier discovery and allow ordinary D0/inactive-blood visits; the D4 referral is optional Side work, not a discovery or Main gate.
- Use NeoForge imports (`net.neoforged.*`), `DeferredHolder`, and `Hemomancy.rloc("snake_case_id")`; do not introduce `net.minecraftforge.*` or Forge-era provider/registration patterns.
- Shared small helpers live in `common/util`; use them instead of private copies: `HemoEasing` for easing and lerp (never `Mth.smoothstep`, which is quintic), `AttributeModifiers.sync` for held modifiers, `ArmorSets.isFullSet`, `ProgressionGates` for degree and Unstained-stage checks (never compare a degree with a literal), `PatternOrigins` for multiblock placement, `HemoTickers.create` in `getTicker`, and `BlockEntitySync.markAndSync` to save and resend a block entity. `EasingCopyGuardrailTest` and `SmallUtilityGuardrailTest` reject new copies.
- A player pays blood only through `BloodAccounting.pay` (one-off) or `payUpkeep` (recurring), with a named `Source{id, category, countsAsSpend, reserveProtected}` constant; it records to `BloodFlowLedger` and ends in `BloodVolumeEvents.syncVolume`, the one owner sync. Never call `drain(`/`subtractBloodVolume(`/`addBloodSpend(` on a player volume or send `BloodVolumeServerPacket` directly; `BloodAccountingGuardrailTest` lists the non-player exceptions. Projected blood reaches a block entity through `ProjectedBloodSink` (default on `IBloodReservoir`).
- A caster chooses targets through `ManipulationCombatHelper`: `canHarm(player, target)` is the strict rule, `canHarm(caster, target, Reach.X)` keeps an older filter's verdicts with a named preset (moving a site to `Reach.STRICT` is a pending decision, G-2b or F-16), and `canHarmFor(source, target)` serves constructs, summons, projectiles and effect holders. A `Monster.class` gather passes `canHarm` in its own arguments (`CombatTargetingGuardrailTest`). Drudge work lives in `DrudgeActions`; heal reductions are `HealModifier` entries applied in one stage; flight is granted and revoked only through `FlightArbiter` (`HealAndFlightGuardrailTest`).
- Subscribers are `@EventBusSubscriber(modid = Hemomancy.MOD_ID)` or `@EventBusSubscriber(modid = Hemomancy.MOD_ID, value = Dist.CLIENT)`, never with `bus=`; the `Hemomancy` constructor adds only mod-lifecycle listeners (`RegistrationStyleGuardrailTest`). Client registration uses the event APIs (`registerBlockEntityRenderer`, `registerSpriteSet`, `RegisterClientExtensionsEvent`), never `BlockEntityRenderers.register` or `initializeClient`.
- Registries live in `common/init/*Init.java`; look a custom-registry entry up by name with `RegistryLookup.byName`, register data components with `registerComponentType`, and put creative-tab entries in `CreativeTabInit` (its one WIP list fills the WIP tab and keeps those entries out of the main tab). Example: `ManipulationInit` holds the blood-manipulation registry and registers entries like `blood_shot` and `vital_effusion` with cost/rank/tendency metadata.
- Manipulation implementations live under `common/manipulation/<tendency>/`; many also define Drudge AI helpers with `setDrudgeAction(...)`, and what an entity (a Will, Vesper) does when it casts one is attached the same way with `setEntityCast(EntityCasts::x)`; `EntityManipulationEffects.cast` only applies the shared rules (`EntityCastGuardrailTest`). New manipulations usually need the class, a `ManipulationInit` entry, lang/model assets, and related docs.
- Particle data is built through `common/particle/HemoParticleData`. A particle that carries only a colour uses `ColorParticleOptions` (its registered type tells it apart), and every Hemomancy particle type is a `HemoParticleType` with its data's codecs; `ParticleDataGuardrailTest` lists the other data classes and rejects per-factory `createData` helpers.
- Render types are built once: a static constant, a school material from `SchoolRenderTypes` (one `Clock` per family, set by its `begin`), or a `SeededRenderTypes` holder keyed by seed (plus any texture or depth flag) whose factory reads a uniforms record. Never build a `RenderType` per call or per frame; `RenderTypeCachingGuardrailTest` rejects it. A holder keeps two types per seed so queued geometry keeps its uniforms; a caller that asks for one seed with three different uniform sets before drawing must end its batch in between.
- School and rite material vertices (U = shape tile, V = seed tile, alpha × 255) are written through `client/render/world/MaterialQuads`; wrap a seed with `MaterialQuads.seedTile`, never `floorMod(seed, 127)` (`MaterialQuadGuardrailTest`). Ferric keeps its own 128-tile constant until decision V-3b.
- Shader noise that two shaders share word for word lives in `assets/hemomancy/shaders/include/noise/*.glsl` and is pulled in with `#moj_import <hemomancy:noise/<name>.glsl>`, one import per include, in dependency order. Seeded noise that reads its shader's own uniforms stays local (`ShaderNoiseIncludeGuardrailTest`). A shader change needs a client launch to prove it compiles; offline validators miss driver errors.
- A boss replays a synced tick counter through `common/entity/boss/BossReplayClock` (`sample` per frame, or `sync` per client tick and `at` per frame) and times moves with `BossMoveTimeline`; never keep a private `tickCount - start` clock (`BossAnimationClockGuardrailTest`).
- Third-person player poses apply through `client/player/PlayerAnimationRegistry.THIRD_PERSON`, in its listed priority order (staff planting, offset reset, casting, then the first claiming pose of microscope, vial injection, torch breath, Unstained swing, living-weapon stroke, then the warp chair); `MixinHumanoidModel` calls only the registry. First-person hand renderers keep their pinned `RenderHandEvent` priorities (`PlayerAnimationGuardrailTest`).
- Client animation time comes from `client/render/AnimationTime`: `partialTick()` (reads 1 under `/tick freeze`), `partialTickWhileFrozen()`, `gameTime(level[, partialTick])` and `age(entity, partialTick)`. Render events and HUD layers pass their own partial tick. Wall-clock animation is listed until decision A-4 (`AnimationTimeGuardrailTest`).
- Screen chrome is shared: borders, bevels, ring borders, corner accents and slot wells come from `ScreenDrawUtils`, and the animated vein background from `VeinBackgroundRenderer` with a per-screen `Style` (`Field`, `Palette`, `Speckles`) that keeps the screen's look. `ScreenChromeGuardrailTest` rejects private copies; a vein field that is different art is listed there with its reason. `ScreenChromeReview` (gameTest, `hemomancy.screenChromeReview`) captures each screen's first frame for before/after comparison.
- For Hemomancy special effects, inspect and prefer the authored Hemomancy/HutosLib visual toolkit before using vanilla particles. Reuse the dynamic glow, cell, tendril, lightning, claw, slash, and related custom effects whenever they can express the intended action; match their color, motion, layering, and intensity to the surrounding blocks, mobs, and items. Vanilla particles are a deliberate fallback for effects the custom suite cannot reasonably express, not the convenience default. This applies especially to bosses, rites, manipulations, impacts, transitions, and other focal moments; do not let otherwise custom visuals become dominated by generic vanilla particle clouds. Before building or upgrading a focal visual, read [the manipulation visual standard](docs/MANIPULATION_VISUALS.md); Hematic Riposte's layered geometry is the reference bar.
- Current resource paths are singular 1.21-style paths already used by this repo: `data/hemomancy/recipe/`, `data/hemomancy/loot_table/`, and `data/hemomancy/dialogue_inquiry/<npc>/<namespace>/<item>.json`. Do not “fix” them to older plural conventions.
- HutosLib owns the book pipeline (`BookPlaceboReloadListener`, the book templates and the guide screens), so check its serializers and reload listeners before inventing local replacements. NPC dialogue is Hemomancy's own (`common/entity/npc/dialogue/`).

## Integration and lore guardrails
- `build.gradle` excludes `compat/mna/**` and `compat/curios/**`; do not reference those packages from core code unless the dependency and source-set gate are explicitly re-enabled.
- JEI compat is live via the local jar; HutosLib is required infrastructure, not optional sugar.
- Keep the existing tone: fungal blood-memory/cosmic infection, morally gray Harbingers, non-saintly Unstained, and no God/Satan framing for the Fungal Entity or Pale Lady.
- Preserve established vocabulary: Harbinger content uses terms like `Hematic Order`, `Sanguine Brotherhood`, `Crimson Lodge`; Unstained content uses `Lethean` / still-water language; enzyme item names intentionally do **not** mirror tendency enum names.

## Documentation contract
- First Separation briefing must check clinical eligibility before recording its advancement. Its two loose vials use a separate explicit issued flag and exact pending count in `PlayerPersisted`, delivered by the `PendingDelivery` claim `BRIEFING_VIALS` with living insertion-confirmed retries and no inferred old-save replacement. Preserve partial/death recovery and one-time helper behavior without awarding collection, tool-claim or rank proof. Keep stale purification/clarity callback controls and teacher guidance aligned.
- First Separation tool rewards serialize exact earned pending stacks under `PlayerPersisted` before recording the one-time claim; the `PendingDelivery` claim `TOOLS` delivers them. Preserve the initialized rack components, count actual insertion rather than Creative discard, retain dead/full-inventory retries, and retry only undelivered tools. Do not infer replacements for historical claims or change proof/promotion gates. Keep teacher guidance and loaded full/partial/death controls aligned.
- First Draws' five-vial gift uses an explicit exact remainder under its existing `PlayerPersisted` state, delivered by the `PendingDelivery` claim `VIALS`. Record delivery from actual insertion, not Creative discard; never drop overflow or deliver while dead. Retry at D1 without widening D2 clinical lessons, preserve partial counts across death, and do not infer replacements for historical briefed saves. Keep teacher/ledger overflow guidance and loaded recovery controls aligned.
- Qliphoth atlas teaching must align `MaterialsData` predicates and `MaterialAtlasSpec` degree gates: Seed/Bloom/Pome/Spine are D7, with ordinary veiled D6 previews. Memory details require witnessed revelation as well as D7. Keep acquisition traces Monolith/Seed/Bloom/Pome/Spine, not deferred Saint trials; atlas knowledge never grants server eligibility or rewards. Preserve authored coordinates and verify native readability separately from loaded predicates.
- Pending First Draws/First Separation supplies and tools, Communion Spine, Vesper Memory and first Mycophant Tendril must defer delivery during observational Chamber visits. `PendingDelivery` applies `ChamberVisitService.isObservational` to every claim, not protected/active flags: timed-chair, attuned and admin visits carry real inventory. Preserve explicit Memory claim migration before deferral. Test exact snapshot recovery, later delivery/components and duplicate refusal without inferring historical claims or changing proof gates.
- First Spine delivery (`PendingDelivery` claim `QliphothBloomEvents.FUNGAL_SPINE`) requires completed Communion, a living player and an actual carried Spine before recording the one-time grant. Ignore Creative discard success; preserve pending degree state through death cloning and fulfill a carried legacy Spine without duplication. Periodic whisper counts are not a prerequisite. Keep original-owner/Bloom-lifecycle recovery and first-projection/forced-return gates separate.
- Vesper Memory uses the same `PendingDelivery` living-player/confirmed-insertion rule as the Tendril; its claim's read keeps the root-key migration. Migrate explicit old root pending claims into `PlayerPersisted` before death cloning, and remove the legacy flag. Do not infer a claim from ending/advancement state or alter owner/Bloom/victory guards. Preserve snapshot compatibility with both old root and nested pending data.
- Unique first Mycophant Tendril delivery is an earned `PendingDelivery` claim under `PlayerPersisted`, not a full-inventory world drop. Preserve death-copy persistence, living-player login/tick retries, actual insertion and duplicate refusal. Dead-player ticks must retain the claim; `Inventory.add` returning true can mean Creative discard, not insertion. Do not infer replacement claims from old defeated flags or change repeat rewards while repairing delivery. Loaded callback/save/clone fixtures do not prove native combat or cold client recovery.
- Scar teaching must follow the shared Brazier offering lifecycle: ordinary insertion, Blood Projection ignition, then held Blood Absorption through completion. Sneaking retrieves offerings. Keep learning, personal Effigy preparation, and actual loadout commit separate; ownership or dialogue is not the D4 Main proof. Templates/gifts remain usable for known loadouts but cannot replace personal preparation. Preserve existing earned proofs. Update teacher, ledger, advancement, Liber, and activation evidence together.
- Chamber dreams and guided visits share `ChamberVisitService` safety. Reject menu drops before removal, retain cursor items, and restore cancelled world-screen tosses immediately. Snapshot personal crafting inputs and cursor as well as inventory. Clear visit copies before dimension transfer, then restore originals after transfer: vanilla player removal clears the menu during that transfer. Full inventory, armor/offhand, components, recovery, and ordinary timed-chair behavior need mod-loaded coverage. Do not grant attunement through early practice.
- Chair entry must check shared visit/projection overlap and destination availability before granting new binding. Preserve D3 access, completed-sleep/direct controls, owner-paired exit, and existing constructions. Missing-destination fixtures alone do not isolate overlap guards; keep loaded-destination coverage explicit.
- A station's operations live in its block entity (the Scriptorium's `inscribe` / `denature`, the Forge's `startApply`, the Centrifuge's `attemptStartup`); its menu offers and dispatches them and never spends blood, records practice or enchants itself (`StationMenuGuardrailTest`).
- Before changing any station upgrade, read [the shared station-upgrade contract](docs/STATION_UPGRADES.md). Use the shared catalog/progress/rite system: personal eligibility is mandatory, free-kit claims are optional, and crafted/gifted kits never bypass server gates. Preserve in-place state and escrow recovery. Update books/dialogue and activation tests with mechanics; older station-specific plans are not authoritative.
- Every Harbinger Cardinal Rite declares a `purpose` (`self` Threshold, `world` Dominion, `making` Working, `bond` Communion); its floor style must match unless it is `"special": true`. Machines, stations and constructs are Working crafts (`recipe/cardinal_rite/working/`, a `subject` fed in `SUBJECT_FEEDING`, offerings escrowed through `RiteOfferingEscrow`, settled once). Only the pinned floorless roster stays a Blood Structure, and Blood Structures take no offerings. Keep `CardinalRitePurposeDataTest`, `WorkingCraftRosterDataTest` and the style-level selector test green when adding rites or crafts; see `docs/HEMOMANCY_REFERENCE.md` §5.3 and §25.1.
- Harbinger rites and crafts share one Liber map (Rites & Crafts) whose families are grouped by purpose in `HarbingerRecipeMapDefinitions`; keep `RecipeMapPurposeGroupDataTest` green and file a new rite's family in its purpose's group. JEI lists rites per purpose. Special rites use special floors that declare their `purpose` (`SpecialFloorDataTest`). A completed Harbinger rite leaves a rite space over its floor until that floor or Focus goes; `hemomancy:rite_bound/*` tags limit blocks, items and entities to matching spaces. Never rite-bind something a player needs before their first completed rite.
- If mechanics, progression, recipes, lore, or player-facing behavior change, check whether `docs/HEMOMANCY_REFERENCE.md`, `docs/LORE_REFERENCE.md`, `docs/MNA_COMPATIBILITY_BRAINSTORM.md`, or the relevant `wiki/*.md` pages also need updates before calling the work done.
